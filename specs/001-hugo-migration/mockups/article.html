Monitoring JVM Applications with Jolokia and JMXTrans

2016-01-24 12 min read
monitoring java jolokia jmx

JMX (Java Management Extensions) is the standard way to expose operational metrics from JVM applications. However, JMX's RMI-based protocol is notoriously difficult to work with — firewalls hate it, monitoring tools struggle with it, and configuration is often fragile. Jolokia solves this by exposing JMX data over HTTP/JSON, making it trivially easy to integrate with modern monitoring stacks.

Architecture Overview #

The monitoring pipeline we'll build has three components: Jolokia as the JMX-to-HTTP bridge, JMXTrans as the metric collector, and your choice of time-series database (InfluxDB, Graphite, or OpenTSDB) as the storage backend.

Jolokia runs as a JVM agent or WAR file inside your application. It exposes all MBeans via a RESTful API. JMXTrans polls these endpoints on a configurable interval and routes the metrics to one or more output writers.

Setting Up Jolokia #

The simplest way to add Jolokia is as a JVM agent. Download the agent JAR and add it to your application's startup flags:

java -javaagent:jolokia-jvm-1.6.2-agent.jar=port=8778,host=0.0.0.0 \
     -jar your-application.jar

Once running, you can verify Jolokia is working by hitting the version endpoint:

curl http://localhost:8778/jolokia/version | python -m json.tool

This returns a JSON response with the agent version and server information. You can then query any MBean attribute:

# Get heap memory usage
curl "http://localhost:8778/jolokia/read/java.lang:type=Memory/HeapMemoryUsage"

# Response:
{
  "request": { "mbean": "java.lang:type=Memory" },
  "value": {
    "committed": 524288000,
    "init": 268435456,
    "max": 3817865216,
    "used": 187432960
  }
}

Configuring JMXTrans #

JMXTrans reads a JSON configuration file that defines which servers to poll, which MBeans to query, and where to send the results.

Basic Configuration

Create a JSON file at /etc/jmxtrans/myapp.json:

{
  "servers": [{
    "host": "localhost",
    "port": 8778,
    "queries": [{
      "obj": "java.lang:type=Memory",
      "attr": ["HeapMemoryUsage"],
      "outputWriters": [{
        "@class": "com.googlecode.jmxtrans.model.output.InfluxDbWriterFactory",
        "url": "http://influxdb:8086",
        "database": "metrics"
      }]
    }]
  }]
}

Advanced Queries

For production use, you'll want to monitor garbage collection, thread pools, and application-specific MBeans. Key metrics to collect:

  • Heap memory — committed, used, max (early warning for OOM)
  • GC pauses — count and cumulative time per collector
  • Thread counts — active, daemon, peak (detect thread leaks)
  • Class loading — loaded count, unloaded count (detect classloader leaks)

Building Grafana Dashboards #

With metrics flowing into InfluxDB, creating Grafana dashboards is straightforward. Start with a single overview dashboard showing the four golden signals for your JVM:

  1. Latency — Request processing time
  2. Traffic — Request rate / throughput
  3. Errors — Error rate and exception counts
  4. Saturation — Heap utilization, thread pool usage, GC pressure

The key insight is that JVM saturation metrics are often the earliest indicators of application problems. A rising heap watermark or increasing GC pause frequency typically precedes user-visible latency degradation by minutes or hours.

Conclusion #

Jolokia plus JMXTrans provides a reliable, low-overhead pipeline for getting JVM metrics into your monitoring stack. The HTTP/JSON approach eliminates the operational headaches of native JMX while preserving access to the full MBean tree.
